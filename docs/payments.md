# Bank/card payments, monthly dues, and reminders

Open **Balances → Manage payments**. Existing manual repayment recording still works.

- Link a US bank account to pay using Stripe Checkout. Account/routing numbers are entered only on Stripe's hosted page. Stripe supports instant verification or its hosted microdeposit verification flow. A method must finish setup before use.
- Add a credit/debit card using Stripe Checkout. Card numbers and CVCs never enter SplitCart's forms, storage, logs, or database. Unsupported/unknown card funding types are rejected.
- Set up a separate receiving bank through Stripe Connect Express onboarding. Receiving requires the recipient's identity/bank verification, active transfers capability, and enabled payouts. Deposits follow Stripe's payout schedule; this is not an instant transfer or payroll service.
- Review principal, surcharge, and total before paying another active roommate or SplitCart. The server computes **2.5% on credit cards only**, rounded to the nearest cent. Bank and debit have no surcharge. A $10.20 credit payment costs $10.46; the recipient receives $10.20. Stripe's processing fees are the platform's cost and are not added as another customer surcharge. App payments are available only when `APP_DUES_CENTS` is configured by the operator; the client cannot choose that price.
- A fixed monthly due specifies the recipient, amount, and day (1–28, UTC). Reminder-only dues do not require a linked payment method or the recipient to have a receiving bank. Enable bank autopay and authorize the amount/method before saving. It does not automatically calculate a changing household balance. Pause the due to retain it without future charges or due reminders, or cancel it to remove it; a payment already in flight can still complete. Autopay uses bank accounts only, avoiding recurring card surcharges. Edit the amount, due day, or selected bank in place. Resuming or changing bank autopay requires fresh authorization. Pending payments retain their original amounts. The next automatic charge is shown in UTC.
- Opt into email and/or text reminders 7, 3, or 1 days before, or on the due date. These apply to saved monthly dues. Emails use the authenticated account's verified email. Texts require Twilio Verify ownership verification, a verified account email, and explicit opt-in. Verification requests are limited to one per minute and five per hour per account. Turn channels off in the app; email messages have an unsubscribe confirmation link. Configure Twilio Advanced Opt-Out for STOP/START; Twilio blocks opted-out deliveries and the service disables the local SMS preference when Twilio reports error 21610. Re-enabling after STOP also requires START at Twilio and enabling the app preference.

## Demo versus live

Demo mode has sample bank/card/receiving accounts, fee previews, simulated one-time payments, and locally persisted plans/preferences. The displayed code `123456` verifies only a demo phone. No real details are requested, no funds move, and no recurring charges/text/email jobs run in demo mode. Reset demo data clears payment demo preferences/history too.

Live processing uses the `payments` Supabase Edge Function and all migrations, including `202611180002_payment_experience.sql` and `202611180003_payment_verification_updates.sql`. Apply the new migration before deploying the updated function. The current repository includes no provider credentials or deployed payment service. No live transfer, live notification, hosted provider onboarding, physical-device return flow, or production scheduler has been validated by the local tests.

## Activate a test integration

1. Configure a Supabase project and existing application auth/database using README.md. Enable authenticator-app (TOTP) MFA in Supabase Auth. Financial linking requires a verified email plus a TOTP-backed AAL2 session established within five minutes; it is enforced by the service after authenticating the same token with Supabase. Install the Supabase CLI and Deno 2.6+. Authenticate the CLI through its secure login flow and link the project (`supabase link --project-ref YOUR_PROJECT_REF`), then apply **all** migrations in filename order using `supabase db push`. Do not reset a production database.
2. Create a Stripe Connect platform approved for your household-dues/payment business model. Enable Express accounts, US transfers, cards, US bank debits, and Financial Connections/hosted verification. Stripe eligibility for roommate transfers and card surcharging varies; confirm platform approval and applicable card-network/local requirements before switching to live keys. The implementation currently supports **USD and US bank accounts only**. All other existing app currencies remain available for expense tracking and manual repayments.
3. Copy `supabase/functions/.env.example` to the ignored `.env.local` alongside it. Enter server credentials securely there or in Supabase's Edge Function Secrets settings. Never put server keys in the mobile/web `.env`, public Expo variables, Git, screenshots, or chat. `SUPABASE_URL` and `SUPABASE_SERVICE_ROLE_KEY` are supplied by hosted Supabase. Use test Stripe keys first. Set `APP_URL` to the accessible HTTPS web app's root URL; it controls CORS and provider return URLs. Native apps open hosted pages externally; return to the app and use Refresh payment status afterward.
4. Provision a Twilio Verify service and a Messaging Service with a registered sender, country permissions, opt-out handling, and fraud/rate controls. Trial accounts send only to approved numbers. Configure the four Twilio variables in the example. Configure a Resend verified sending domain and `REMINDER_FROM_EMAIL` plus `RESEND_API_KEY`. Set a strong random `PAYMENT_JOB_SECRET` (separate from all provider keys). `APP_DUES_CENTS=0` disables SplitCart app dues; set an integer cent amount of at least 50 to offer app payments.
5. Upload server secrets with `supabase secrets set --env-file supabase/functions/.env.local`, then `supabase functions deploy payments`. The committed function config disables gateway JWT verification **only because the handler separately authenticates all user actions with Supabase `getUser`, webhook requests with Stripe signatures, and jobs with the independent scheduler bearer secret**. Do not remove those checks.
6. Register `https://YOUR_PROJECT.supabase.co/functions/v1/payments/webhook` in Stripe for `payment_intent.succeeded`, `payment_intent.processing`, `payment_intent.payment_failed`, `payment_intent.canceled`, `payment_intent.requires_action`, `charge.refunded`, and `charge.dispute.created`. Put its signing secret in `STRIPE_WEBHOOK_SECRET`. Use matching test/live modes. Webhook retries and app status polling reconcile payments from Stripe, rather than trusting browser redirects. Set `PAYMENTS_ENABLED=true` in **server secrets** for testing once configuration is complete.
7. Start the app with live Supabase public credentials and `EXPO_PUBLIC_DEMO_MODE=false`. Create two test users in one USD household. Verify both emails. Complete the in-app authenticator check before recipient Express onboarding and sender bank/card setup on Stripe's hosted pages. Finish any hosted bank test-deposit verification, then refresh. Only successful bank SetupIntents qualify a saved bank for payments. Refresh payment status when returning. Exercise credit/debit/bank payments, card authentication, failed/processing payments, and webhook retries using Stripe's official test methods. Only succeeded principal enters the repayment ledger; a pending ACH payment does not. Never also record a successful bank/card payment manually.
8. Configure the recurring job below and test reminder delivery to controlled, opted-in test contacts. Verify disabled channels, phone verification failures, email unsubscribe, Twilio STOP, due cancellation, recipient leaving the household, insufficient funds, duplicate scheduler invocations, and an ACH return after initial success. Review failed deliveries/charges in the provider dashboards and database. After provider approval and end-to-end validation, switch credentials and webhook to live mode deliberately.

## Recurring job (required for live autopay/reminders)

Call `POST https://YOUR_PROJECT.supabase.co/functions/v1/payments/run` every 15 minutes with `Authorization: Bearer <PAYMENT_JOB_SECRET>` from a trusted scheduler. The job operates on UTC calendar dates. It charges a due once on its due day and sends a reminder once on the chosen reminder date. It does not catch up charges/reminders from missed calendar dates, so monitor scheduler health. It does not debit again after a failed charge; the user must review payment activity. Payment statuses needing authentication can be resumed from the app. Never put the job credential in the client.

For hosted Supabase, enable `pg_cron` and `pg_net` in the dashboard and securely create Vault secrets named `splitcart_payment_job_secret` (matching `PAYMENT_JOB_SECRET`) and `splitcart_functions_url` (the `https://YOUR_PROJECT.supabase.co/functions/v1` base). Then run this non-secret SQL once:

```sql
select cron.schedule('splitcart-payments', '*/15 * * * *', $$
  select net.http_post(
    url := (select decrypted_secret from vault.decrypted_secrets where name='splitcart_functions_url') || '/payments/run',
    headers := jsonb_build_object('Content-Type','application/json','Authorization',
      'Bearer ' || (select decrypted_secret from vault.decrypted_secrets where name='splitcart_payment_job_secret')),
    body := '{}'::jsonb,
    timeout_milliseconds := 10000
  );
$$);
```

Check `cron.job_run_details`, `net._http_response`, and function logs without exposing headers/credentials. A successful HTTP response includes `visited` and `failures`; nonzero failures need investigation. Small household workloads fit a single job; large installations should move to a queue with per-item retry/lease monitoring.

## Reliability and operational boundaries

Payment creation/confirmation uses stable Stripe idempotency keys. A unique `(due_id,due_date)` prevents duplicate monthly charges. The unconfirmed PaymentIntent is persisted before confirmation. An ambiguous create older than 23 hours is blocked for operator review instead of risking a new debit after Stripe expires its idempotency record. Never delete ambiguous payment records or rotate request IDs to force a retry. Browser retries retain the original request id; canceled/failed payments need a new, explicitly reviewed request.

`complete_payment` atomically updates payment status and inserts principal into the ledger once; only the server service role can call it. Payment/contact/provider tables are inaccessible to anonymous or authenticated SQL clients. User-facing API queries are explicitly scoped to the authenticated user. Recipient household membership, method ownership, fees, and app-dues prices are checked server-side at the moment of charging. Leaving/changing households stops scheduled processing for the old household.

Refund/dispute events and a confirmed late bank-payment failure remove the repayment credit and flag the order. Partial refunds conservatively revoke the entire ledger credit and require operator reconciliation; automated proportional adjustments and dispute-resolution reinstatement are not implemented. Perform refunds and appropriate destination-transfer reversals through the Stripe dashboard/approved operations workflow. Connect platform balances, processing costs, fraud, ACH returns, disputes, and negative balances require operator monitoring. A confirmed payment can later be reversed by a return/dispute.

Reminder attempts are claimed before sending so overlapping jobs cannot spam users. Resend also receives a stable idempotency key. A provider error or ambiguous timeout is marked failed and **is not blindly retried** (Twilio cannot guarantee exactly-once SMS sends). Review `payment_reminder_deliveries` and provider logs for manual resolution. “Sent” means accepted by the provider, not proof of inbox/phone delivery. The current release does not ingest downstream delivery/bounce callbacks. Failed automatic payments create a private in-app warning and a separately deduplicated failure email/text for users with opted-in, verified channels. These alerts do not automatically retry a debit. Future changes should add a durable queue and delivery webhooks for higher-volume operation.

## Upcoming payments, requests, receipts, and account alerts

The home dashboard shows upcoming scheduled dues, recipient, UTC due date, autopay/paused state, next automatic charge, and payments needing attention. **Balances → Upcoming** can pay an individual scheduled occurrence. A completed occurrence advances to the next month. Processing and authentication-required payments retain their occurrence and explain the next step; only confirmed principal updates balances. Receipts/history show Pending, Processing, Completed, Failed, Canceled, Refunded, Disputed, or Action needed with guidance.

Payment from **Pay due** is linked to `(due_id,due_date)` and serialized with scheduler claims. Only one order can claim that occurrence. A completed or in-progress occurrence suppresses ordinary pay reminders; failed/disputed/refunded occurrences get guidance instead of another instruction to pay. A manually recorded repayment or unrelated one-time payment does not clear a scheduled occurrence or cancel autopay. Pause a schedule if it has been handled outside this flow. Old schedules without explicit dates in local demo storage assume the current day as their start; live schedules retain their creation timestamp.

**Requests** supports a specific amount, an optional note, and a purchase attachment. A request does not create a second expense or alter shares. Only its payer can fund it, and the receiving roommate needs completed bank onboarding for live payments. Only the requester can cancel an unclaimed request. Request payment/cancellation are serialized by a row lock; an active or completed payment blocks another payment. Refunds/disputes require support review before repayment. Preview requests are shared across local preview logins in the same browser; live requests are participant-scoped within the active household. The request list currently shows the latest 100 requests.

**Activity** searches outgoing history by recipient, masked method, friendly status, amount, and payment reference. Download a text receipt in the browser or save/share it through the native share sheet. Pending/failed receipts explicitly state that they are not proof of payment; demo receipts say no money moved. Older payments without a stored masked method show it as unavailable. Receipt history is fetched in pages and is not limited to the last 30 payments.

The latest private account alerts appear in **Upcoming**, including schedule creation/edits/pauses/cancellation, payment-method setup/removal, reminder-setting changes, received requests, and failed autopay. They are in-app alerts; payment-setting changes do not send security email/SMS. No notification permission or push provider is required. Failure-email/text delivery still requires the configured providers and scheduler/webhook setup above.

Before release, apply migrations without resetting existing data, deploy the updated function, and test multiple accounts, concurrent tabs/jobs, early/manual due payment, late ACH returns, schedule pauses/edits, and provider delivery failures with test credentials. These operational steps have not been run against a hosted project by this change.


## Verification and notification release notes

Migration `202611180003_payment_verification_updates.sql` stores bank setup-session references and deduplicated payment-message attempts, and adds explicit cash/other/bank-card ledger labels. These new tables remain service-only with RLS enabled. No account/routing numbers, card PAN/CVC, authenticator seeds, or one-time security codes are stored by the payment service. Authenticator enrollment secrets are displayed transiently by Supabase’s client enrollment flow and cleared from the component after verification; do not log or persist them. Only an unverified authenticator enrollment can be restarted in the UI. Enrollment does not replace an existing verified factor.

Bank-link progress is retrieved from the user’s own Stripe Checkout/SetupIntent records. Verification URLs require a fresh two-step check and never appear in the ordinary status response. Setup URLs and provider-hosted verification should be tested with Stripe’s official test flows; receiving-bank readiness is separate from paying-bank ownership. A fresh check is required for linking cards and receiving accounts too. MFA protects linking; this release does not introduce a universal MFA login gate or a self-service MFA recovery bypass. Operators must establish an identity-verified recovery process for lost authenticators.

The Activity view shows Started → Processing → Completed for outgoing and incoming roommate payments. Completed means the provider-confirmed payment entered the household ledger; it does not promise that the recipient’s separate bank payout has arrived. Incoming history includes the latest 100 entries and excludes sender payment-method and fee details. Cash remains an outside-payment record, with no bank/card surcharge or processor status.

Enable **Email/text advance autopay notices** or **Email/text payment status updates** under Reminders, plus the desired verified email/text channels and consent. Advance notices contain the amount, masked bank, UTC charge date, and how to review/pause autopay. They are sent one day ahead; schedules created too late do not receive a retroactive advance notice. An enabled advance notice replaces the ordinary one-day-before reminder for that autopay occurrence. Paused or already-claimed/paid occurrences do not receive new charge notices.

Payment updates cover pending (created/processing grouped once), successful, failed, and bank-authentication-required events. The sender and an active receiving roommate each use their own preferences. The job scans newly created orders from the last seven days, reconciles in-progress Stripe intents, and claims updates; signed webhooks and status refresh also produce them. Existing orders have `notify_events=false` to avoid historical notification bursts. A late ACH failure can produce a failure update after an earlier success. Disables/unsubscribes/STOP apply to these channels too. Duplicate webhook/job invocations do not resend a claimed event. Provider failures/timeouts are recorded for operator review rather than blindly retried; delivery acceptance does not prove inbox/handset delivery. Payment updates are informational and never request a second debit while a payment is pending. Cash records do not generate processor-status notices.
